# ADR-0014: クラス名ハッシュは正規化した内容の固定長ハッシュとし、命名は注入可能にする

- **Status**: Accepted
- **Date**: 2026-09-18
- **Deciders**: yutaura

## Context

クラス名は `` css`...` `` の中身から内容ハッシュで生成している（ADR-0004 の短縮リネームの前段）。この生成方針に 3 つの不安定さがあった。

1. **書式ゆらぎに追従する**: ハッシュ入力が `` css`` `` の生テキストだったため、インデント幅・改行・コメント・末尾セミコロンの有無でクラス名が変わった。Prettier の設定変更だけで全クラス名が変わり、SSR した HTML と配信 CSS の長期キャッシュが無駄に失効する。さらに「同一内容の `` css`` `` はファイルを跨いで同一クラス名に収束させ、重複排除の基盤にする」という設計意図自体が、書式が違うだけで成立していなかった
2. **名前の長さが可変**: 32bit を base36 にするだけだったため桁落ちで 3〜9 文字とばらついた（ADR-0004 は「9 文字」を前提に書かれており記述とズレていた）
3. **命名方針が固定**: 内容ハッシュ以外の命名（デバッグしやすい名前にする、他ツールの規約に合わせる、暗号学的ハッシュにする）を選べなかった

## Decision

**ハッシュ入力を正規化し、ハッシュ長を固定し、命名そのものを注入可能にする。**

1. **正規化（`normalizeCssForHash`）を自前で持つ**: 空白の畳み込み・コメントの空白化・区切り記号まわりの整形・末尾セミコロンの除去だけを行う。文字列リテラルの中身は保持し、`:` の直前の空白は残す（`& :hover` と `&:hover` は別セレクタのため）
2. **ハッシュ長を base36 7 桁に固定**する（`36^7 > 2^32` で 32bit を桁落ちなく表現できる最小桁数）。クラス名は常に `bc` + 7 = 9 文字
3. **命名戦略（`NamingStrategy`）を注入できる**: `hash`（ハッシュアルゴリズムのみ差し替え）/ `className` / `keyframesName` / `classNamePrefixes`。Vite プラグイン・webpack loader・テスト用 `` css`` ``（`createCss`）のすべてで同じ値を渡す

これを成立させるため、短縮リネーム（ADR-0004）の**接頭辞依存を外した**。`applyRename` と頻度集計はリネーム表のキー（実際の名前）で照合する。ただし CSS アセットのセレクタからの収穫（ADR-0013）は「どれが bestcss の生成名か」を接頭辞でしか判別できないため、名前の形を変える利用者には `classNamePrefixes` の宣言責任を渡す。

## Alternatives Considered

- **Lightning CSS の minify 結果をハッシュ入力にする**: ADR-0002 の基盤に一貫し、`#ffffff` → `#fff` のような値の等価表記まで収束する。採用しなかったのは、lightningcss のバージョンを上げると出力が変わり得るため、**依存更新だけで全クラス名が変わる**新たな不安定さを招くから。クラス名の決定要因は自分たちの管理下に置く
- **ハッシュ空間を広げて衝突耐性を上げる（64bit 化など）**: 衝突は「別スタイルの静かな誤適用」という致命的な故障モードを持つが、実測では 8 万ブロックで衝突 0 件であり、最終的に ADR-0004 で全数確認のうえ短縮されるため今回は据え置いた。衝突検出は別の判断として切り出す
- **ゼロパディングではなく 6 桁に切り詰めて 1 文字短くする**: `36^6 < 2^32` なので衝突確率が 2 倍になる。bc 名は ADR-0004 で最終的に 1〜2 文字へ短縮されるため、長さは出荷サイズにほぼ影響しない。安全側を採った
- **注入は「ハッシュ関数だけ」に限る**: API は小さくなるが、「名前の付け方」を変えたい要求（接頭辞、デバッグ用の可読名）に応えられない。`defaultName` を入力に渡すことで、包むだけの用途も 1 行で書けるようにした
- **webpack で命名戦略を JSON クエリで css loader へ渡す**: 関数を含む値は JSON に載らない。モジュールスコープの受け渡し表（`naming-registry.ts`）で共有する形にした

## Consequences

### Positive

- 書式の変更（再インデント、コメントの増減、Prettier 設定の変更）でクラス名が変わらず、SSR した HTML と配信 CSS の長期キャッシュが保たれる
- 「同一内容はファイルを跨いで同一クラス名へ収束する」が書式の違いを越えて実際に成立し、重複排除（および ADR-0013 のライブラリ／アプリ間の合流）がより効く
- クラス名が常に 9 文字になり、短縮前の HTML サイズが内容に依存しなくなる
- 短縮リネームが接頭辞の規約から独立し、`bc` 以外の名前でも機能する
- アセット名のハッシュ（`assets/bestcss.<hash>.css`）がクラス名と分離され、ファイル名文字列が短縮リネームに誤ってマッチし得る潜在バグが消えた

### Negative

- このバージョンを跨ぐと**既存の全クラス名が変わる**（正規化とゼロパディングの導入による）。クラス名を固定値として期待しているスナップショットは更新が必要
- 正規化は書式ゆらぎに絞ったため、値の等価表記（`#ffffff` と `#fff`、`0px` と `0`）や結合子まわりの空白（`&>.b` と `& > .b`）は別のクラス名になる
- 命名戦略を注入した場合、決定性と一意性の責任は利用者側に移る（非決定的な関数は dev と build、client と server ビルドで名前を食い違わせる）
- webpack では命名戦略をモジュールスコープの表で loader 間に渡すため、loader を別プロセスで走らせる構成（thread-loader 等）では成立しない

### Neutral

- `contentHash` は正規化を行わない素のハッシュとして残る（アセット名・dev のキャッシュキー用）。正規化を含むのは `generateClassName` / `generateKeyframesName` の側
