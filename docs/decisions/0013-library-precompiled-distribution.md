# ADR-0013: コンポーネントライブラリはプリコンパイル配布を正とし、ソース配布は非対応

- **Status**: Accepted
- **Date**: 2026-07-06
- **Deciders**: yutaura

## Context

bestcss で書いた UI ライブラリを npm 配布する経路が未検証だった（ロードマップ棚卸しで検出）。配布モデルは 2 つ考えられる:

1. **ソース配布**: css`` を含むソースをそのまま出荷し、利用側のビルドで抽出する
2. **プリコンパイル配布**: ライブラリのビルド時に抽出済みの JS + CSS を出荷する

## Decision

**プリコンパイル配布を正とする**。ライブラリ作者は `minifyClassNames: false` でビルドし、bc 名（内容ハッシュ）のまま出荷する。最終的なクラス名短縮・重複排除は利用側アプリのビルドが行う。

これを成立させるため、Vite プラグインの generateBundle は短縮対象を「自前生成のクラス名」に加えて **CSS アセットのセレクタ（.bc...）からも収穫する**ように変更した（webpack プラグインは元から同じ自己完結方式）。

ソース配布は非対応とし、transform は node_modules 内のファイルをスキップし続ける。

## Alternatives Considered

- **ソース配布（利用側で抽出）**: コロケーションのまま配布できるが、(a) 利用側に bestcss の導入とバージョン整合を強制する、(b) dev サーバーの依存事前バンドル（optimizeDeps）はプラグインの変換を通らず、css`` が実行時エラーになる組み合わせが生まれる。境界が曖昧になる割に利得が薄い
- **短縮名のまま出荷**: 短縮名（a, b, c...）はビルドローカルの頻度順で、利用側アプリの短縮名と衝突する。bc 名は内容アドレスなので衝突せず、むしろライブラリとアプリの同一スタイルが同一クラス名へ収束して重複排除まで働く

## Consequences

### Positive

- 利用側は import するだけで bestcss の設定が不要（どのバンドラーでも使える）
- 内容ハッシュの合流により、ライブラリとアプリの同一宣言は配信 CSS で 1 ルールになる
- 利用側ビルドがライブラリ由来のクラスも短縮するため、サイズ最適化が配布境界を跨いで効く

### Negative

- ライブラリ作者にビルド工程（Vite lib モード + sideEffects 宣言）が必要
- `bc` プレフィックスのクラス名は実質的に予約となる（アセット収穫の regex が `.bc[a-z0-9]+` を短縮対象とみなすため、手書き CSS で bc 始まりの短いクラス名を使うと誤って短縮される可能性がある）
